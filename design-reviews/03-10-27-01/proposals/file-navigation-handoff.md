## Type-aware file links

HTML `<a href>` and supported Markdown file links use the same destination routing. Ordinary click or Return on a focused reading link follows it directly; right-click is optional. While editing Markdown, ordinary clicks continue to place the caret/select text: retain the deliberate link-follow route from the editing model rather than making content clicks navigate away.

| Target | Proposed result |
|---|---|
| `.html` / `.htm` | HTML viewer, authored CSS within its surface, document JavaScript off. |
| `.md` / `.markdown` | Rendered Markdown reader or the retained active rich-edit session if already open. Navigation never saves/discards the draft. |
| Supported image | Existing image-view pattern with fit/zoom/pan and file identity. A linked image is a destination, distinct from an image embedded in the source page. |
| Other regular local file, e.g. `report.pdf` / `notes.txt` | A **File details** tab with name, selectable path, available file facts and “Preview unavailable.” Show **Open in {resolved app name}** and **Show in Finder**, enabled only when the relevant capability/handler/grant is available. With an unknown handler, show disabled Open in default app plus a reason. Screen 13 uses Preview as an illustrative resolved handler, not a claim about the user’s default app. No PDF/text/editor renderer is promised here. This is proposed capability, not proof that the app accepts every type today. |
| Missing/inaccessible target | Retain source and history cursor; distinguish “Linked file not found” from access required. Native Choose file… is a deliberate file-only grant; Cancel leaves state intact. Mismatched selection explains the issue instead of silently changing target. |

Other-file tabs participate in history even when they cannot be previewed. Following a link opens File details, never silently launches an executable or arbitrary external application. The labeled default-app action is a separate deliberate command; no-handler or launch failure retains the file tab and offers an honest reason/Retry where useful. File details remains the current visit after an external launch; the reader cannot track navigation inside other apps. Backend acceptance/metadata/launch rules, including executable types and packages, require explicit canonical/security handoff reconciliation. Unknown actions are disabled with a reason until supported. A folder target is identified as a folder, not misrendered as a file or treated as a new root grant.

Resolve relative hrefs from the file that contains them, then route the **resolved target type**. Example: `personal/docs/guide.html` with `images/diagram.png` leads to `personal/docs/images/diagram.png`; `README.md` leads to the Markdown file beside the source; `report.pdf` leads to File details. Nested/parent-relative paths work inside valid grants; paths, encoded characters, symlinks and author `<base>` cannot broaden access. Each destination's local assets resolve from that destination. Do not resolve from the app install directory. Cross-file fragments apply only when meaningful for that renderer; unsupported fragments disclose that the file opened but the location could not be applied. Missing HTML/Markdown anchors never imply a successful section jump.

A same-file anchor jump is a visit to a new location, so Back can restore the prior passage without creating a new file tab. Empty fragment means page start. Newly opened files without a fragment begin at their normal initial position; an already open file without a fragment keeps its retained position. General link menu: **Open linked file**, Copy link address, Copy link text, View destination details. An intentional secondary click on a link while rich editing uses **Follow link** as a separate menu command; normal editing clicks/Return remain text operations, preserving the section draft and source selection. Anchor-only primary action: Go to section. Return activates a focused menu row; unmapped copy actions have no invented global chord, and ⌘C copies selected text. Full authored href/resolved path remains selectable. Unsupported URL schemes/automatic redirects remain inert; web/mail routing is outside this local-file addendum and does not gain a new capability.

The Settings tree filter changes visibility only: checked Documents and images only shows directories, Markdown, HTML and supported images; other file entries appear when unchecked. A link may open another type in File details while its tree row stays filtered. Existing tabs/history remain reachable; no hidden row is forcibly revealed. The image/detail reference screens illustrate the filter unchecked where `report.pdf` is visible. Filename search may return allowed file names; contents search must honestly state which types are indexed. No new all-format contents search is implied.

## Visit history: testable state rules

1. **Record real navigation.** Successfully activating a different file through a document link, project tree, Open file/native entry, search result, Documents list or tab click appends a visit. Same file + meaningful different fragment/search passage/outline target appends a location visit. Selecting the already active file at the same location does nothing. Plain scrolling, typing, Save, recovery checkpoints, refresh, theme/font changes and tab reordering do not append visits.
2. **Seed and scope.** Each workspace window has its own sequence, initially the first opened/current restored file. Existing restored tabs are not fictitious prior visits until activated. History is retained in memory for the current window session only, with the approved 100-entry design bound; restart persistence is excluded from this revision and is not an existing capability. Recent files is a separate acquisition list.
3. **Traverse without recording.** Back moves to the preceding committed visit; Forward moves to the following one. Example: `README.md → guide.html → diagram.png → report.pdf`. From `report.pdf`, Back activates `diagram.png`; Back again activates `guide.html`; Forward activates `diagram.png`. The cursor moves only after navigation succeeds. Do not append visits on traversal or trigger a loop of tab-selection events. Rapid/stale async results must not commit the wrong file/cursor.
4. **Branch like a browser.** After Back, an ordinary new successful navigation truncates the forward branch and appends the new visit, even if the chosen file has an existing tab. Example: A → B → C, Back to B, then open D: A → B → D. C's tab remains open; only the old forward path disappears. Selecting C later is a new visit. Failed/cancelled navigation, merely opening a menu or activating the current file does not truncate the branch.
5. **Restore context, not historic bytes.** Retain a location for each visit: document anchor/relative offset, image zoom/pan/fit, and the relevant focus/selection/session state. Ordinary file switches record the departure location; same-file passage jumps retain the previous location before moving. Revisit an open file with its current content/unsaved draft, not an old content snapshot. Changed/deleted anchors use nearest surviving context with honest feedback. History never means Undo, Save, discarding content or bypassing recovery/conflict guards.
6. **Retain drafts.** Back/Forward behaves like ordinary tab switching: keep/pause the current rich section and acknowledged recovery state, preserve per-tab edit undo/caret and resume safely on return. If navigation requires a close/root replacement/reselection with loss guards, run the existing guard. Cancel, save failure or unacknowledged required recovery leaves source/cursor/forward branch unchanged. Do not introduce automatic Save as a history side effect.
7. **Closed and unavailable targets.** A history entry can remain after its tab closes. Traversal reopens the file through current access/version/recovery checks, then restores context. It does not resurrect a deliberately discarded draft. Deleted/ungranted entries are not silently removed/skipped: explain which destination is unavailable, retain source/cursor, offer Retry/Choose file… as applicable and Visited files… to pick another entry. A root change revalidates old visits; history never recreates an old grant silently.
8. **Close and empty states.** Closing an inactive tab is not a visit. Closing the active tab and revealing another file records that newly active file after loss guards finish. Closing the last tab suspends the history cursor in the empty surface; it does **not** add an invented empty-file visit. Back from that surface reopens the most recent committed file at the retained cursor, under current grant/recovery checks; Forward remains disabled until a file is active. If that target fails, keep the empty surface and offer Visited files… rather than auto-skipping. Once reopened, ordinary Back/Forward semantics resume; empty workspace is not a Forward destination. Opening a new file from empty records one successful visit and applies normal forward branching. First-ever empty window has both directions disabled.
9. **Focus and overlays.** File change dismisses contextual menus/tooltips anchored to the prior file. Pointer activation keeps focus on the Back/Forward control so repeated traversal is predictable; keyboard menu invocation returns focus to that same control/tab strip. Announce “Back to {filename}” / “Forward to {filename}” and location once after success. Direct link/search/outline activation focuses the destination passage; keep its source focus location for return. Focus never returns to a removed/inactive target. Failure dialog returns to the invoking control; no orphaned floating actions.

## Acceptance criteria — runtime NOT TESTED

- Open HTML → follow Markdown link → follow image link → open another file in File details. Click and Return use the same type/grant-aware route. Back and Forward traverse all four, restore context and retain drafts.
- Independently visit files through tree, tabs, search, Open/native entry and Documents. Every real activation participates in the same window history; image or Markdown navigation needs no HTML file in the sequence.
- A → B → C; Back to B; new visit D produces A → B → D and disables Forward. Cancel/access failure leaves A → B → C and its cursor intact. Back/Forward themselves never append or duplicate tabs.
- First/latest/empty/closed/deleted/ungranted/loading cases follow the rules above. Reopening history never silently widens grants, replays old writes or resurrects discarded edits.
- Buttons, Go menu, keyboard activation and visited-file menus agree on destination and enabled state. Search Return to Explorer affects only the sidebar. Keyboard focus and menu dismissal remain correct during traversal.
- Unsupported preview shows filename/path, explicit default-app/reveal routes and universal history; disabled/no-handler/launch-failure reasons remain honest. No PDF or arbitrary-file rendering claim; no automatic external execution on link click.
- Narrow/enlarged/ES layouts keep Back/Forward, file identity and Save/Return where applicable reachable. HTML/CSS remains contained; document scripts/handlers/executable URLs do not run.

## Critique refinement: access and errors

Screen 11 shows Cancel initially focused and the resolved requested path, not only a relative href. Dialog details expose both href and resolved path with selectable wrapping text. Choose file opens the native picker. Picker cancellation returns to this dialog; cancelling the dialog returns focus to the source link. A mismatched selection explains the requested vs selected file, retains source/cursor/branch, and offers Choose again / Cancel; it must not silently open a different destination. Successful selection commits one visit only after the destination is available.

Access required, missing file and unsupported destination are separate outcomes. A readable other-file File details tab is a successful visit; a missing-file attempt is not. The selected default-app action must identify the actual resolved app when known. No-handler/launch failure retains the File details visit. Executable/package launch policy remains unresolved; disable launch for those cases until a canonical/security decision exists. The explicit reveal/details route remains available where supported.

The 100-entry bound and empty-window behavior are approved design decisions; technical validation remains pending. Test that ordinary tab switches sharing this history feel predictable; if participants cannot forecast Back after tab/tree changes, revise the visit model before implementation instead of assuming browser familiarity proves it.
